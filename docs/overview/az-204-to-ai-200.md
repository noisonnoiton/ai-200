# AZ-204에서 AI-200으로

Azure 개발자 자격증을 준비해 왔다면 AI-200은 완전히 새로운 시험이라기보다, 기존 AZ-204의 범용 Azure 개발 기반 위에 **AI backend workload와 production 운영 역량을 전면에 배치한 후속 시험**으로 보는 편이 정확합니다.

AZ-204는 Azure에서 애플리케이션을 개발하는 전반적인 능력을 평가했습니다. AI-200은 그중에서도 컨테이너 기반 backend, AI data, vector search, messaging, serverless integration, secret 관리와 distributed observability를 하나의 AI cloud solution으로 연결하는 능력에 초점을 둡니다.

!!! warning "자격증의 관계"
    AZ-204는 2026년 7월 31일 23:59 Central Standard Time에 폐지되었습니다. AI-200은 AZ-204 자격증의 단순한 시험명 변경이 아니라, **Azure AI Cloud Developer Associate**라는 새로운 역할과 범위를 대상으로 하는 시험입니다.

## 한눈에 보는 변화

| 관점 | AZ-204 | AI-200 |
| --- | --- | --- |
| 자격증 역할 | Azure Developer Associate | Azure AI Cloud Developer Associate |
| 중심 문제 | Azure 애플리케이션을 어떻게 개발하고 배포하는가? | AI backend solution을 어떻게 개발하고 운영하는가? |
| compute | App Service, Functions, ACI, Container Apps, autoscaling, deployment slots | ACR과 ACR Tasks, App Service, Container Apps revision, KEDA, AKS manifest와 troubleshooting |
| data | Cosmos DB와 Blob Storage | Cosmos DB for NoSQL, PostgreSQL + pgvector, Azure Managed Redis, vector indexing과 similarity search |
| integration | API Management, Event Grid, Event Hubs, Service Bus, Queue Storage | Service Bus의 queue/topic/subscription과 dead-letter, Event Grid filter/retry, Functions trigger/binding |
| security | Entra ID, Microsoft Identity, SAS, Microsoft Graph, Managed Identity, Key Vault | Key Vault secret rotation/retrieval, App Configuration, AI backend의 secret과 configuration 경계 |
| observability | Application Insights의 metric, log, trace, availability test, alert | OpenTelemetry 기반 distributed trace와 KQL을 이용한 log/metric 분석 |
| 언어·개발 전제 | Azure SDK, CLI, PowerShell 등 범용 Azure 개발 경험 | Azure SDK와 third-party SDK, Python, vector database, containerized application 경험 |

## AZ-204에서 다루던 내용

폐지되기 전 AZ-204는 Azure Developer Associate 역할에 맞춰 애플리케이션 개발 lifecycle 전체를 다뤘습니다. 공식 skills measured는 다음 다섯 영역으로 구성되었습니다.

### Azure compute solutions 개발

- Azure Container Registry에 container image를 게시하고 Azure Container Instances로 실행
- Azure App Service Web App 생성과 설정
- App Service의 진단, logging, TLS, API settings, service connections, autoscaling, deployment slots
- Azure Functions app, input/output binding, data operation·timer·webhook trigger
- Azure Container Apps를 이용한 애플리케이션 구현

### Azure storage 개발

- SDK를 이용한 Azure Cosmos DB container와 item 작업
- Cosmos DB consistency level과 change feed notification
- Blob Storage의 property와 metadata
- Blob data 작업과 storage policy, lifecycle management

### Azure security 구현

- Microsoft Identity platform과 Microsoft Entra ID를 이용한 인증·인가
- Shared Access Signature(SAS)
- Microsoft Graph 연동
- Azure App Configuration과 Azure Key Vault
- Key, secret, certificate를 사용하는 코드와 Managed Identity

### 모니터링과 troubleshooting

- Azure Monitor Application Insights의 metric, log, trace 분석
- Availability test와 alert
- 애플리케이션 또는 서비스에 Application Insights instrumentation 적용

### Azure 및 third-party service 연결

- Azure API Management instance와 API 생성·문서화·access 설정·policy
- Azure Event Grid, Event Hubs, Service Bus, Queue Storage를 사용하는 event/message 기반 solution

즉 AZ-204는 특정 AI workload보다 **Azure에서 일반적인 애플리케이션을 구현하는 데 필요한 서비스 폭**이 넓었습니다. Storage도 Cosmos DB와 Blob Storage 중심이었고, integration도 API와 여러 messaging service의 기본적인 연결이 중요한 축이었습니다.

## AI-200에서 달라진 내용

AI-200은 기존 Azure 개발 개념을 버리지 않습니다. 대신 AI workload가 실제로 동작하는 backend를 만들 때 필요한 병목과 운영 문제를 더 구체적으로 묻습니다.

### 1. 범용 compute에서 container platform으로 중심 이동

AZ-204의 compute 영역은 App Service Web Apps, Functions, ACI, Container Apps와 배포 설정을 폭넓게 다뤘습니다. AI-200에서는 container를 단순히 실행하는 것보다 **image lifecycle, orchestration, scale-out, 운영 진단**이 중요해졌습니다.

- ACR에서 image를 build, store, version, manage
- ACR Tasks로 image build와 실행
- App Service에 container를 배포하면서 environment variable과 secret 연결
- Container Apps의 environment configuration과 revision management
- KEDA를 활용한 event-driven scaling
- AKS에 manifest로 application 배포
- AKS와 Container Apps의 log, event, end-to-end connectivity troubleshooting

따라서 AZ-204의 `어디에 애플리케이션을 배포할 것인가`라는 선택 문제에서 AI-200은 `containerized AI backend를 어떻게 versioning하고, scaling하고, 고장 지점을 추적할 것인가`로 무게중심이 이동합니다.

### 2. 일반 storage에서 AI data와 vector search로 확장

AI-200의 가장 큰 변화는 data 영역입니다. Cosmos DB를 단순한 document store로 사용하는 데서 끝나지 않고 embedding과 semantic retrieval을 다룹니다.

- Cosmos DB for NoSQL의 query, indexing policy, consistency level, RU 최적화
- embedding 저장과 vector similarity search
- change feed processor를 이용한 item 변경 처리
- PostgreSQL schema와 data type, index 설계
- `pgvector`를 이용한 vector search와 RAG pattern
- metadata filter를 포함한 semantic retrieval
- vector workload에 맞춘 PostgreSQL compute, memory, storage, connection 최적화
- Azure Managed Redis의 cache, expiration, invalidation
- Redis vector index를 이용한 similarity search

AZ-204의 Cosmos DB와 Blob Storage가 애플리케이션 data를 저장하는 방법에 초점을 뒀다면, AI-200은 **embedding을 어디에 저장하고, 어떻게 검색하고, operational data와 어떻게 결합해 RAG backend를 만들 것인가**를 묻습니다.

### 3. service 연결에서 AI workflow integration으로 구체화

두 시험 모두 event와 message 기반 설계를 중요하게 보지만, AI-200은 장시간 실행되는 AI backend 작업과 비동기 처리를 더 명확하게 전제합니다.

- Service Bus queue로 backend 작업을 분리
- topic과 subscription으로 consumer를 분리
- dead-letter queue를 처리해 실패한 message를 복구·분석
- Event Grid의 custom event, filter, retry
- Azure Functions의 trigger와 binding으로 serverless API와 workflow 구현
- Functions app configuration과 deployment

AI 요청은 모델 호출, data retrieval, 후처리처럼 시간이 오래 걸리거나 재시도가 필요한 단계로 나뉘기 쉽습니다. 그래서 AI-200에서는 단순히 service를 연결하는 것보다 **message와 event를 구분하고, retry와 dead-letter를 포함한 reliable workflow를 설계하는 능력**이 중요합니다.

### 4. 인증 중심 security에서 secret·configuration 운영으로 초점 보강

AZ-204에는 Entra ID, Microsoft Identity, SAS, Microsoft Graph, Managed Identity 같은 identity 주제가 포함되어 있었습니다. AI-200의 공식 범위는 이보다 좁은 형태로 보이지만, AI backend를 운영하기 위한 secret과 configuration 관리가 분명해졌습니다.

- Key Vault에서 secret을 안전하게 저장·조회·rotation
- App Configuration에서 애플리케이션 configuration 관리
- container와 serverless 환경에 secret을 직접 넣지 않고 runtime에 주입

AI service endpoint, database connection, signing key, embedding 관련 설정이 여러 component에 걸쳐 사용될 수 있으므로, AI-200에서는 **secret 자체의 보호뿐 아니라 configuration이 compute와 어떻게 연결되는지**까지 함께 봐야 합니다.

### 5. Application Insights 중심에서 distributed tracing과 KQL로 확장

AZ-204도 Application Insights를 이용한 metric, log, trace, availability test와 alert를 포함했습니다. AI-200은 분산된 AI backend에서 하나의 요청이 여러 service를 통과한다는 점을 전제로 observability를 더 구체화합니다.

- OpenTelemetry SDK로 service 간 distributed trace 구현
- KQL로 log와 metric 분석
- container, Functions, messaging, data service 사이의 correlation 확인
- 실패가 발생한 component와 지연 구간을 end-to-end로 좁히기

AI-200에서 monitoring은 단순히 `Application Insights를 켜는 방법`이 아니라, **하나의 AI request가 어떤 service와 data path를 통과했는지 증명하고 troubleshooting하는 방법**에 가깝습니다.

## 무엇이 그대로 이어지는가

AI-200을 준비한다고 해서 AZ-204 학습 내용을 모두 버릴 필요는 없습니다. 다음 기반은 그대로 유효합니다.

- Azure SDK client 생성과 authentication
- App Service와 Azure Functions의 기본 구조
- Container image와 registry 개념
- Cosmos DB의 partition, consistency, SDK 접근
- Managed Identity와 Key Vault
- Event Grid, Service Bus의 event/message 모델
- Application Insights와 Azure Monitor
- Azure CLI를 통한 resource와 deployment 관리

다만 각 주제를 AI workload에 맞게 다시 연결해야 합니다. 예를 들어 Cosmos DB를 공부할 때 document CRUD만 복습하는 것으로는 부족합니다. embedding, vector search, RU와 indexing trade-off, metadata filter까지 이어서 이해해야 합니다.

## AZ-204 학습자의 전환 전략

### 그대로 가져갈 것

1. Azure SDK와 resource model 이해
2. App Service, Functions, container 배포 기초
3. Cosmos DB, Key Vault, Managed Identity
4. Event Grid와 Service Bus의 기본 semantics
5. Application Insights와 Azure Monitor 사용 경험

### 새로 보강할 것

1. Python 기반 Azure SDK 실습
2. ACR image lifecycle과 ACR Tasks
3. Container Apps revision, KEDA, AKS manifest
4. PostgreSQL와 `pgvector`
5. Cosmos DB vector search와 RAG retrieval
6. Azure Managed Redis cache와 vector index
7. Service Bus dead-letter와 retry 설계
8. OpenTelemetry instrumentation
9. KQL을 이용한 distributed troubleshooting

### 학습 순서

1. **Container platform**: ACR → App Service 또는 Container Apps → AKS 흐름을 직접 배포합니다.
2. **AI data**: embedding을 Cosmos DB 또는 PostgreSQL에 저장하고 vector similarity search를 실행합니다.
3. **Integration**: AI 작업을 Service Bus message로 분리하고 Event Grid 또는 Functions로 후속 처리를 연결합니다.
4. **Security**: Key Vault와 App Configuration을 사용해 secret과 runtime configuration을 외부화합니다.
5. **Operations**: OpenTelemetry trace와 KQL query로 하나의 요청을 끝까지 추적합니다.
6. **Trade-off 복습**: cache와 source of truth, message와 event, Container Apps와 AKS를 요구 사항에 따라 선택합니다.

## 결론

AZ-204가 **Azure application developer의 공통 기반**을 평가했다면, AI-200은 그 기반을 사용해 **운영 가능한 AI backend solution을 만드는 developer**를 평가합니다.

따라서 AZ-204에서 AI-200으로 이동할 때 핵심은 기존 내용을 처음부터 다시 공부하는 것이 아닙니다. 기존의 compute, storage, security, integration 지식을 다음 질문으로 재구성하는 것입니다.

- containerized AI workload는 어디에서 실행하고 어떻게 scale할 것인가?
- embedding과 operational data는 어떤 storage와 index로 관리할 것인가?
- 장시간 AI 작업의 retry와 dead-letter를 어떻게 설계할 것인가?
- secret과 configuration을 각 component에 어떻게 안전하게 공급할 것인가?
- 하나의 요청이 container, message, function, database를 거치는 동안 어디서 실패했는지 어떻게 증명할 것인가?

이 질문에 코드와 Azure resource를 직접 연결해 답할 수 있다면, AZ-204의 기반을 AI-200의 production AI 개발 역량으로 전환할 수 있습니다.
